# 模型平台评测模块 · 现状工作流梳理

> 本文档基于对 `quanta_eval_platform.py`（评测子模块，383KB）与 `toolchain_demo.py`（主应用集成层）的代码走读整理，描述**当前 Demo 已实现的评测工作流**，作为后续产品重新设计的现状基线（as-is baseline）。
>
> 生成日期：2026-07-16

---

## 一、结论先行：真实流程 vs 之前的简化描述

之前概括的流程是：

```
提示词设计 → Benchmark 创建 → 评测任务生成 → 双盲标注 → BT-Davidson 排行榜
```

这个描述**方向正确，但过于简化**，遗漏了几个关键环节。代码里的真实流程更接近：

```
[配置阶段]  标签体系 + 提示词 + 场景 + 评分标准 → 组装 Benchmark
                                                      ↓
[任务阶段]  创建评测任务（绑定 Benchmark + 待测模型 + 评测类型）
                                                      ↓
[执行阶段]  数据采集（真机/云端跑模型）→ 评测打分（人工标注）
                                                      ↓
[结果阶段]  评测结果记录 → 分析报告 → BT-Davidson 排行榜
```

三个重要差异：

1. **评测不止"双盲"一种**。代码支持 4 种评测类型（成功/失败、量表评分、偏好对比、基线对照），双盲 A/B 只是其中的 `preference` 类型。
2. **"采集"和"打分"是分离的两步**。先有一步把模型跑起来采集执行数据（`/collect`），再有一步人工看数据打分（`/evaluate`）。之前的描述把这两步合并了。
3. **配置层是四件套的组装**：标签、提示词、场景、评分标准四者独立管理，再由 Benchmark 把它们组合起来。之前只提到了"提示词 + Benchmark"。

## 二、核心概念与数据模型

评测模块围绕以下几个核心对象构建（均为内存 Mock 数据，无数据库）：

| 对象 | 代码变量 | 说明 |
|------|----------|------|
| 模型 | `MODELS` | 待测/基线模型，含版本、架构、参数量、状态（如 Spirit v1.5、π₀ 等） |
| 标签体系 | `TAXONOMY` | 三级分类的能力标签树：**能力标签**（空间理解/物体理解/长程任务/推理…）+ **动作标签**（拾取/放置/开合…）+ 场景标签 |
| 提示词 | `PROMPTS` | 两层结构：**高层级指令**（High-level，如"整理桌面"）+ **低层级子任务**（Low-level，如"拾取红色糖果"），每个子任务挂能力/动作标签 |
| 场景 | `SCENES` | 物理评测环境定义：工作空间尺寸、光照、台面、物体清单（位姿/尺寸/材质）、参考图片与演示视频 |
| 评分标准 | `CRITERIA` | 评测表单定义，绑定 4 种类型之一，规定打分项（如"进度分 0.0~1.0" + "偏好选择" + "文字说明"） |
| Benchmark | `BENCHMARKS` | **配置组装的产物**：一个场景 + 一组提示词 + 一个评分标准 |
| 评测任务 | `EVAL_TASKS` | **执行单元**：绑定 Benchmark + 待测模型列表 + 评测类型 + 目标样本数 + 优先级 |
| 评测会话 | `EVAL_SESSIONS` | 单次打分记录，是排行榜计算的原始数据（policy_a, policy_b, preference, progress…） |

### 4 种评测类型（`CRITERIA_TYPES`）

| 类型 | key | 说明 |
|------|-----|------|
| 成功/失败 | `pass_fail` | 每个模型独立判定二元成功或失败 |
| 量表评分 | `scale` | 按刻度打分（如进度分 0~1），每个模型独立评分 |
| **偏好选择** | `preference` | **两两对比，选更优方或平局**（即双盲 A/B，RoboArena 标准用的就是这个） |
| 基线对照 | `baseline` | 与基线模型对比，判定胜/负/平 |

> 说明：Benchmark `b4`（综合能力评测 v1）的描述里明确写了"用于 RoboArena 对标"，`c1` 评分标准直接命名为"RoboArena 标准"。可见现有评测框架就是围绕 RoboArena 那套双盲偏好方法搭建的——这正是你 MT 说"后面不用这个模式了"所指的对象。

## 三、完整工作流（分阶段拆解）

### 阶段 0 · 公共配置（一次性搭建，可复用）

对应导航栏"公共配置"分组，四个独立管理页：

| 步骤 | 路由 | 做什么 |
|------|------|--------|
| ① 标签管理 | `/tags` | 维护能力/动作/场景标签树，是提示词打标的字典 |
| ② 提示词管理 | `/prompts` | 创建高层级指令 + 低层级子任务，给子任务挂标签 |
| ③ 场景管理 | `/scenes` | 定义物理评测环境（物体、光照、参考视频等） |
| ④ 评分标准 | `/criteria` | 定义打分表单结构，选择 4 种评测类型之一 |

这四者相互独立，可各自复用。

### 阶段 1 · 组装 Benchmark

| 路由 | 做什么 |
|------|--------|
| `/benchmarks` → `/benchmarks/create` | 把【一个场景 + 一组提示词 + 一个评分标准】组合成一个可复用的评测基准 |

Benchmark 是"评测什么 + 怎么评"的固化模板。数据结构：
```python
{"scene_id": "s1", "prompt_ids": ["p1","p2","p3"], "criteria_id": "c1"}
```

### 阶段 2 · 创建评测任务

| 路由 | 做什么 |
|------|--------|
| `/tasks` → `/tasks/create` | 选一个 Benchmark，指定**待测模型列表** + 评测类型 + 目标样本数 + 优先级 |

任务是真正跑评测的执行单元。创建后初始状态为 `未开始`。

任务状态机（代码注释明确）：
```
未开始 → 采集中 → 评测中 → 评测完成 → 分析完成
              ↘ 已暂停  ↘ 已废弃
```

任务还携带 `ckpt_id` 字段，用于与训练 Checkpoint 建立**血缘关联**（这是它挂在模型平台下的关键意义）。

### 阶段 3 · 数据采集（跑模型）

| 路由 | 做什么 |
|------|--------|
| `/collect` | 列出状态为"采集中"的任务 |
| `/collect/<id>/setup` | Step 0：选项目 / 模式 / 设备 / 部署方式（真机 Franka / 云端部署） |
| `/collect/<id>` | Step 1：场景准备（按 Benchmark 场景摆好物体） |
| `/collect/<id>/run` | Step 2：实际执行，让模型在场景中跑任务，采集执行数据 |

> ⚠️ 代码里这个模块顶部有红色提示："本模块为**采集端功能**，页面仅示意用"。说明采集这一环在真实产品里是由**采集端/真机侧**完成的，工具链里只是占位示意。

### 阶段 4 · 评测打分（人工标注）

这里有**两个并行的工作台**，对应提示词的两个层级：

| 路由 | 页面标题 | 做什么 |
|------|----------|--------|
| `/evaluate` | 评测工作台 **HL**（High-level） | 高层级视角打分 |
| `/evaluate2` | 评测工作台 **LL**（Low-level） | 低层级子任务逐条打分，分步骤推进 |
| `/evaluate/<id>/submit` | — | 提交打分，写入 `EVAL_SESSIONS` |

双盲工作台（`preference` 类型）的核心逻辑：
- 从任务的待测模型里**随机抽两个**（`random.sample(model_ids, 2)`）作为 policy_a / policy_b，隐藏真实身份
- 标注员看两方执行视频，采集三维数据：**进度分**（progress_score 0~1）+ **二元偏好**（A 胜 / 平局 / B 胜）+ **文字说明**
- `/evaluate2` 会把 Benchmark 里所有提示词的低层级子任务拍平成步骤序列，逐条 `step=0,1,2...` 推进标注

### 阶段 5 · 结果、分析与排行

| 路由 | 页面 | 做什么 |
|------|------|--------|
| `/eval-records` | 评测结果 | 查看评测记录，支持"任务视角"和"Checkpoint 视角"两种切换 |
| `/tasks/<id>` | 任务详情 | 单任务的执行数据与结果 |
| `/analysis` | 多维分析报告 | 按能力标签/场景等维度的分析 |
| `/leaderboard` | 排行榜 | **BT-Davidson 算法**根据所有 `EVAL_SESSIONS` 的两两对比计算模型排名 |

**BT-Davidson 排行榜算法**（`fit_bt_davidson`，Section 2）：
- Bradley-Terry 模型的 Davidson 平局扩展，输入是所有 `(policy_a, policy_b, outcome)` 对比三元组（outcome: 2=A胜 / 1=平 / 0=B胜）
- 梯度上升迭代拟合每个模型的实力参数 θ，含自适应学习率衰减
- 输出：分数（θ×200+1500，类 ELO 分制）、标准差、胜/负/平场次、对局数
- 结果按会话数缓存（`_RANKINGS_CACHE`）

## 四、集成到主工具链的方式（`/model/eval/*`）

评测子模块以独立 Flask app 存在（独立跑在 5001 端口），集成进主应用时：

1. 主应用遍历 `ep.app.url_map`，把所有路由加 `/model/eval/` 前缀重新注册
2. 拦截 `render_page`，把子模块页面塞进主应用统一的门户布局
3. HTML 里的链接自动重写加前缀

**关键：主导航只暴露了子模块的一部分页面**。模型平台左侧栏"评测"分组只挂了 3 个入口，"公共配置"挂了 4 个：

```
评测:      评测任务(/tasks) · 评测结果(/eval-records) · 工作台(/evaluate2)
公共配置:  Benchmark 管理 · 场景管理 · 提示词管理 · 标签管理
```

而独立模块里还有 `/collect`、`/evaluate`(HL)、`/leaderboard`、`/analysis`、`/criteria` 等页面**没有挂到主导航**。这说明集成时做过一轮裁剪，主平台里评测的呈现是简化版。

> 注意：主导航里这些评测入口的状态标记大多是"**待定**"，而公共配置是"优化/新增"。这本身就暗示评测部分是**待重新设计**的重点区域——正好对应你这次的任务。

## 五、给产品重新设计的观察点

基于现状代码，梳理出几个后续设计时值得关注的点：

1. **RoboArena 双盲偏好是当前的核心范式**。整套配置（评分标准 c1、Benchmark b4）都是围绕它建的。若要弃用这个模式，需要想清楚：新范式用哪种评测类型？现有的 `pass_fail` / `scale` / `baseline` 三种是否够用，还是要引入全新范式？

2. **"采集"与"打分"分离的设计是否保留**。当前采集端是占位示意，真实产品里采集在真机侧。新设计需要明确工具链侧到底管到哪一步。

3. **HL / LL 双工作台的必要性**。当前有两个并行打分台（高层级 / 低层级），交互复杂。是否需要合并或取舍。

4. **配置四件套（标签/提示词/场景/标准）偏重**。搭一次评测要配置四类对象再组装 Benchmark，前置成本高。新设计可考虑简化配置路径。

5. **血缘关联是模型平台评测的独特价值**。`ckpt_id` 把评测任务和训练 Checkpoint 关联起来，"训练 → 评测 → 排行"闭环是它挂在模型平台下（而非独立评测平台）的核心理由，值得在新设计中强化。

6. **主导航已裁剪**。集成版比独立版少了一半页面，说明产品对"评测在模型平台里该露出多少"已有初步判断，新设计可以此为起点。
