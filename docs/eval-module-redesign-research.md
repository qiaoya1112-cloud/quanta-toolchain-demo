## 第一部分 · 任务总览（给 MT 汇报用）

### 任务是什么

MT 交办：**提前了解并构思模型平台评测模块的产品设计**。核心是理解一次**评测范式的转向**——

> 从「RoboArena 双盲偏好对比」范式（旧，已实现）
> 转向「Skill × Factor 结构化能力诊断」范式（新，文档1 定义的方向）

### 三篇文档的身份与关系

| 文档 | 真实标题 | 性质 | 与本任务的关系 |
|------|----------|------|----------------|
| 文档1 | 评测分类体系设计说明 | **新方法论** | ⭐ 要转向的方向，核心参考 |
| 文档2 | [概要] 模型双盲评测 | 旧模式概要设计 | 思路可参考，模式已弃用 |
| 文档3 | [PRD] 模型双盲评测 MVP | 旧模式详细 PRD | 思路可参考，模式已弃用 |

- 文档 2 + 3 是**一对**（概要 + 详细），描述同一个东西 = RoboArena 双盲模式 = 现有代码实现。
- 文档 1 是**另起一路**的新方法论，是本次任务的落点。

### 一句话结论

现有评测是「黑盒对比」——知道 A 比 B 好，但不知道为什么、哪个能力弱。
新方法论是「白盒诊断」——用控制变量法精确定位「抓取能力在夹持宽度=大时通过率只有 40%」这种**可溯源**的结论。

从「裁判」变成「教练」——不只排名，而是指导训练、定位弱点。

## 第二部分 · 新方法论深度解读（文档1）

### 2.1 五层核心结构

新方法论的骨架是一个五层树：

```
Stage（场域）      评测大类方向
  └─ Story（测试任务）   一个独立测试场景，分两类
       └─ Skill（原子能力）    不可再分的单一机器人能力
       └─ Factor（影响因子）   影响 Skill 表现的可测量参数
            └─ 测试用例         Prompt + 环境配置(factor取值)，最小可执行单元
```

| 层级 | 职责 | 示例 |
|------|------|------|
| **Stage** | 划定评测大类 | 端到端操作评测、预训练 Benchmark |
| **Story** | 定义测试策略和场景 | [专项] 抓取基准测试 / 整理桌面 |
| **Skill** | 标识被测原子能力 | 抓取、放置、物品识别 |
| **Factor** | 描述影响 Skill 的参数 | 夹持宽度、干扰物、指令表达方式 |
| **测试用例** | 具体执行单元 | pick up the red candy（白桌面，仅红糖果） |

**关键点**：每一层职责单一——Stage 定方向，Story 定策略，Skill 是被测对象，Factor 是测试变量，测试用例是执行载体。

### 2.2 Story 的两种类型（方法论的心脏）

这是整套方法论最重要的设计。同样是"测一个任务"，但目的不同，设计方式完全不同。

#### 能力专项 Story（控制变量，找瓶颈）

- **目的**：其他变量统一，系统性测某个 Skill 在单一变量（single factor）不同取值下的表现，找**能力边界**。
- **设计方法**：控制变量法——每次只改变一个 Factor 取值，其余 Factor 保持默认。
- **命名**：`[专项]` 前缀，如 `[专项] 抓取基准测试`。
- **数据价值**：回答"是哪个 Factor 的哪个取值失败率更高"，结论**可溯源**。

示例（测试变量 = 夹持宽度）：

| 用例 | Prompt | Skill | 被测 Factor | 取值 | 其他 Factor |
|------|--------|-------|------------|------|------------|
| T1 | pick up the red candy | 抓取 | 夹持宽度 | 小 | 默认 |
| T2 | pick up the blue bowl | 抓取 | 夹持宽度 | 适中 | 默认 |
| T3 | pick up the watering can | 抓取 | 夹持宽度 | 大 | 默认 |

#### 场景专项 Story（真实流程，测协同）

- **目的**：还原真实使用场景，验证多个 Skill 协同执行的**端到端完成率**，同时通过变体设计积累不同条件下的场景数据。
- **设计方法**：按真实任务流程设计动作序列；每步可有多个**变体**，变体间通过 Key Factor 取值区分；执行时从该步变体池**随机抽取一个**（同序号变体互斥）。
- **依赖关系**：用"前置序号"标识——留空=可独立执行；`1,2`=须全部完成；`1|2`=任一完成即可。
- **命名**：场景名称，如 `整理桌面`。

示例（整理桌面场景，简化）：

| 序号 | 前置 | 变体ID | Prompt | Skill | Key Factor |
|------|------|--------|--------|-------|-----------|
| 1 | — | 1-A | pick up the marker pen | 物品识别 | 对象表达=标准名词 |
| 1 | — | 1-B | pick up the white writing tool | 物品识别 | 对象表达=功能替代 |
| 2 | — | 2-A | pick up the kiwi | 拿取 | 形状=圆形 |
| 2 | — | 2-B | pick up the banana | 拿取 | 形状=条形 |
| 3 | 1\|2 | 3-A | put it into the white box | 放置 | 目标位置=明确容器 |
| 3 | 1\|2 | 3-B | put it on the right side | 放置 | 目标位置=相对方位 |

#### 两类对比

| 维度 | 能力专项 | 场景专项 |
|------|----------|----------|
| 测试目的 | 找单 Skill 能力边界和瓶颈 | 验证多 Skill 协同的端到端完成率 |
| Skill 数量 | 聚焦 1 个核心 Skill | 每步可标注多个 Skill |
| Factor 角色 | 被测变量，穷尽每个取值 | Key Factor 有变体，其余是 preset；随机组合不穷尽 |
| 输出结论 | Skill 在各 Factor 取值下的通过率（精确） | 场景完成率 + 各步骤×Skill 通过率 + Factor 趋势 |
| 适用时机 | 能力定向评估、回归对比、精确归因 | Demo 验收、发布评估、真实场景鲁棒性验证 |

### 2.3 Factor 体系（24 个因子，四大类）

Factor 挂在 Skill 下，是影响该 Skill 表现的可测量参数。能力专项 Story 就是围绕这些 Factor 展开的。

| 分类 | Factor 列表 | 取值示例 |
|------|-------------|----------|
| **被操作物品属性** | 物体形状、夹持宽度、物体尺寸、物体材质、颜色、摩擦力、物体重量、物理属性、运动状态 | 球型/方块/棍形；小/适中/大；静止/运动中 |
| **环境条件** | 摆放密度、干扰物、背景复杂度、光照条件、背景反射度、遮挡程度 | 稀疏/中等/密集；无/部分/严重遮挡 |
| **指令语言** | 动作表达、对象表达、终态表达、指定本体、序数理解、方位理解、相对位置、语义分类 | 标准动词/同义替换/结果导向；第一个/最左边 |
| **任务结构** | 对象数量、目标位置、目标高度、对齐精度 | 单一/固定多个/不定数量；精确对齐/大致放置 |

### 2.4 ID/OOD 泛化评估（不需要单独设计 Story）

这是新方法论的精妙之处——**泛化能力不新增 Story 类型，而是靠给 Factor 取值打标签，从同一份能力专项数据里聚合出来**。

- **ID（In-Distribution）**：训练分布内的常见条件 → 统计**基线成功率**
- **OOD（Out-of-Distribution）**：分布外的泛化测试条件 → 统计**泛化成功率**

**两层分析**：

第一层 · Skill 维度汇总（跨所有 Factor 取值）
| Skill | 总用例 | 通过 | 基线得分(ID) | 泛化得分(OOD) |
|-------|--------|------|-------------|--------------|
| 抓取 | 27 | 18 | — | 67% |
| 放置 | 15 | 12 | — | 80% |
| 物品识别 | 12 | 6 | — | 50% |

第二层 · Skill × Factor 下钻（找拖累泛化的具体取值）
| Skill | Factor | 取值 | 通过率 |
|-------|--------|------|--------|
| 抓取 | 夹持宽度 | 小 | 90% |
| 抓取 | 夹持宽度 | 适中 | 85% |
| 抓取 | 夹持宽度 | 大 | 40% ↓ 瓶颈 |

**分析路径**：泛化得分低 → 下钻 Skill×Factor → 找到具体短板 → 定向优化。

**设计闭环**：能力专项定位瓶颈 → 优化后回测同一组用例验证提升 → 场景专项验证整体效果同步改善。

## 第三部分 · 新旧范式对比与迁移分析

### 3.1 范式根本差异

| 维度 | RoboArena 模式（旧·文档2/3·已实现） | 新方法论（文档1） |
|------|-----------------------------------|-----------------|
| 核心动作 | 两模型双盲 A/B 对比，人选谁更优 | 按 Skill×Factor 拆解，逐条测通过率 |
| 组织结构 | 提示词(1HL+NLL) → Benchmark → 任务 | Stage → Story → Skill+Factor → 用例 |
| 打分方式 | 进度分 + 二元偏好 + 文字说明 | 通过率 / 成功失败（按因子聚合） |
| 核心产出 | BT-Davidson 排行榜 | ID/OOD 泛化得分 + Skill×Factor 瓶颈 |
| 回答的问题 | "哪个模型整体更好" | "哪个能力在哪个条件下失败" |
| 产品哲学 | 裁判（排名） | 教练（精确归因） |

### 3.2 现有代码 → 新方法论的映射

现有 `quanta_eval_platform.py` 是旧模式的完整实现。落地新方法论时的对应关系：

| 现有对象（旧） | 新方法论对应 | 变化程度 |
|---------------|-------------|----------|
| 提示词 HL/LL 两层 | Story（能力专项/场景专项） | 🔴 重构：从"文字对比"变成结构化任务 |
| 能力标签（空间/物体理解…） | Skill（原子能力） | 🟡 演进：能力标签是 Skill 雏形 |
| 动作标签（拾取/放置…） | Skill（部分） | 🟡 演进 |
| （无） | Factor 体系（24 因子 + ID/OOD） | 🔴 全新：核心新增 |
| Benchmark（场景+提示词+标准） | Story/用例集合 + 标准 | 🟡 组装模式保留，内容换 |
| 场景管理 | Stage/场景专项的环境定义 | 🟢 大致可复用 |
| 双盲工作台 + 偏好打分 | 用例执行 + 通过率打分 | 🔴 打分逻辑重做 |
| BT-Davidson 排行榜 | ID/OOD 泛化得分 + 下钻报告 | 🔴 统计维度重做 |
| 评定标准四类型（pass_fail 等） | 能力专项主要用 pass_fail | 🟢 数据结构可直接接 |

图例：🟢 可复用 · 🟡 演进 · 🔴 需重建

### 3.3 旧模式中可复用的设计资产

MT 说"设计思路和过程可以参考"。以下是**跨范式仍成立**的资产：

1. **采集与评测分离**（文档2 决策点）——边界清晰、评测客观、数据可解耦复用。新方法论同样需要这个架构原则。
2. **双盲机制**——评测员看不到模型身份，屏蔽主观干扰。
3. **评定标准四类型 + 统一数据结构**（`pass_fail/preference/baseline/scale`）——能力专项高度依赖 `pass_fail`，这套结构可直接接。
4. **Benchmark 组装思想**——(场景+提示词+标准) 换成 (场景+Story+Skill/Factor+标准)，组装模式一致。
5. **checkpoint 拆包为采集任务、任务状态机、进度分归一化、中译英处理**——范式无关的工程能力。
6. **"通用能力 + 场景封装"分层思想**（文档2）——对新方法论的 Stage 概念天然契合。
7. **lowlevel 配对打分的方案讨论**（文档3 附录）——关于"失败信号不能被掩盖、不重复惩罚"的统计原则，对新方法论设计通过率聚合时同样适用。

## 第四部分 · 新评测模块产品形态构思

> ⚠️ 以下是**初步构思**，供讨论，非最终设计。目的是把方法论落成可讨论的产品雏形。

### 4.1 配置体系的重构

旧的"四件套"（标签/提示词/场景/标准）需要重组为新方法论的层级：

```
【能力字典层】（一次性搭建，全局复用）
  Skill 库      — 原子能力定义（抓取/放置/识别…）
  Factor 库     — 24 个影响因子 + 取值 + ID/OOD 标签
  Skill×Factor  — 每个 Skill 关联哪些关键 Factor

【测试设计层】
  Stage 管理    — 评测大类方向
  Story 编辑器  — 能力专项（控制变量表格）/ 场景专项（变体序列）
  测试用例生成  — 由 Story + Factor 取值笛卡尔组合自动生成

【执行与结果层】
  评测任务      — 绑定 Story 集合 + 待测 checkpoint
  执行工作台    — 用例逐条执行 + 通过/失败打标
  诊断报告      — ID/OOD 泛化得分 + Skill×Factor 下钻热力图
```

### 4.2 关键页面设想

| 页面 | 核心功能 | 新增/复用 |
|------|----------|-----------|
| Skill & Factor 管理 | 维护能力字典、因子取值、ID/OOD 标签 | 🔴 全新（最核心） |
| Story 编辑器 | 两种模式：控制变量表 / 变体序列表 | 🔴 全新 |
| 测试用例预览 | 展示 Story 展开后的用例列表 | 🔴 全新 |
| 评测任务 | 绑 Story + checkpoint + 设备/优先级 | 🟡 改造现有 |
| 执行工作台 | 逐用例执行 + pass/fail 打标（可保留双盲） | 🟡 改造现有 |
| **诊断报告** | Skill 泛化得分表 + Skill×Factor 下钻 | 🔴 全新（替代排行榜） |

### 4.3 交互难点（需要重点设计）

1. **Story 编辑器的两种模式**——能力专项是"控制变量表格"（选 Skill、选被测 Factor、列取值），场景专项是"带依赖的变体序列表"。这是全新且复杂的编辑交互。
2. **测试用例的自动生成**——能力专项要按 Factor 取值笛卡尔展开，需要预览+裁剪机制，避免用例爆炸。
3. **ID/OOD 标签的录入位置**——是打在 Factor 取值上（全局），还是打在用例上（局部）？文档1 倾向前者（Factor 取值级）。
4. **诊断报告的可视化**——Skill×Factor 热力图、泛化得分下钻、瓶颈高亮，是新方法论价值的最终呈现，也是产品的"高光页面"。
5. **场景专项的执行调度**——每步从变体池随机抽取、处理前置依赖，执行逻辑比旧的线性 lowlevel 复杂。

## 第五部分 · 待明确的开放问题

留给后续与 MT / 算法团队对齐：

1. **旧的 BT-Davidson 排行榜是否彻底废弃**？还是"能力诊断"和"排行榜"并存（诊断对内指导训练，排行对外/对标）？
2. **双盲机制在新范式里是否保留**？能力专项是单模型测通过率，不一定需要双盲；但多 checkpoint 横测时可能仍需要。
3. **Factor 的 24 个是否固定**？是否需要支持算法团队自定义扩展？
4. **能力专项 vs 场景专项的优先级**——MVP 先做哪个？（建议：能力专项更结构化、更易落地，可先行）
5. **Skill 体系与现有"能力标签/动作标签"如何平滑迁移**——是重建还是在现有标签基础上演进？
6. **ID/OOD 标签谁来定**——需要算法团队提供训练数据分布信息才能准确标注。
