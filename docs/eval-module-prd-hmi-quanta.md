## 2. 需求理解总结

### 2.1 核心问题

具身评测组当前面临的核心问题是：**现有 HMI 采集端无法满足评测场景的特殊需求**。

具体表现为：
1. **配置不灵活**：评测需要频繁调整 Prompt、模型版本、评分规则，但当前系统需要提前导入、无法现场调整
2. **数据记录不全**：缺少模型推理日志（MozTrace）、本体执行轨迹、三方视频等关键过程数据
3. **数据导出混乱**：导出的表格 ID、时间戳无序，无法清晰对应单次测试的多轮结果（T1/T2/T3...）
4. **版本管理缺失**：代码版本、数据集版本、配置版本无法追溯和复用
5. **启动流程受限**：必须插连 Pico 头显才能启动，限制了测试调度自由度

### 2.2 需求本质

业务方希望建设的是：**一个面向评测场景的专用数据管理和执行平台**，而不是简单的采集工具改造。

核心诉求包括：
- **配置化框架**：评测集、Prompt、Metric 字段、评分规则都需要灵活配置和模板化管理
- **数据湖能力**：统一存储、多维检索、聚合分析、版本追溯
- **执行自动化**：一键启动多组件（movax + 本体轨迹 + MozTrace）、自动上传、异常处理
- **闭环回流**：BadCase 一键回流训练数据湖

### 2.3 与现有系统的关系

**文档明确提到的关系：**
- **HMI 采集端**需要针对评测场景做适配，与采集任务在计算口径、开发逻辑上做区分
- **数据平台（数据湖）**作为底层基础设施，评测模块复用其存储、检索、版本管理能力
- **已有评测平台（quanta_eval_platform）**的关系文档中**未明确说明**

**推测关系（待确认）：**
- 已有评测平台可能承担"双盲评测、模型排行榜"等功能，与本次需求的"真机评测执行"是互补关系
- 本次需求更侧重**真机执行过程中的数据采集、过程记录、配置管理**

### 2.4 确定与不确定的内容

**文档明确写出的内容：**
- ✅ 当前痛点清晰（版本兼容、启动限制、配置不灵活、日志不全、导出混乱）
- ✅ 需求按优先级拆解（P0/P1/P2 三级）
- ✅ 数据架构完整（评测集/评测任务/Segment 三层模型）
- ✅ 核心设计原则（平台与业务解耦，平台提供通用能力，业务定义规则）
- ✅ Metric 字段需要用户自定义（字段名、数据类型、模板化）

**目前不确定的内容：**
- ❓ **功能归属边界**：哪些功能应该放在 HMI 采集端，哪些应该放在已有评测平台，哪些需要新建模块
- ❓ **数据流转路径**：评测数据从 HMI 上传后，是直接进数据湖，还是先经过评测平台处理
- ❓ **离线评测能力**：文档提到"后续接入仿真能力"和"CICD 流程"，但细节未明确
- ❓ **Benchmark 执行方式**：Benchmark 表格中的测试是手动执行还是自动执行，执行频率是什么
- ❓ **失败分类体系**：文档提到失败分类（fail_category/fail_subcategory），但具体分类标准未定义
- ❓ **权限控制**：提到"分层权限控制"，但角色定义、权限粒度未明确

## 4. 业务流程梳理

### 4.1 完整评测流程（基于文档内容整理）

```
┌─────────────────────────────────────────────────────────────────┐
│ 阶段 1: 配置准备                                                 │
└─────────────────────────────────────────────────────────────────┘
  1.1 创建评测集（或选择 Benchmark）
      └─ 定义 Prompt 列表、场景标签
      └─ 配置 Metric 字段（自定义字段名和类型）
      └─ 保存为模板（可选）
           │
           ▼
  1.2 创建评测任务
      └─ 选择评测集 / Benchmark
      └─ 指定被测模型（Policy、版本、ckpt 路径、代码分支）
      └─ 配置执行参数（每个 Prompt 测试次数、超时时长）
      └─ 选择测试机器（从 IP 列表中选择）
           │
           ▼
  1.3 模型和代码部署
      └─ 推送 checkpoint 到指定机器
      └─ 根据代码分支拉取依赖包
      └─ 验证部署状态

┌─────────────────────────────────────────────────────────────────┐
│ 阶段 2: 执行采集                                                 │
└─────────────────────────────────────────────────────────────────┘
  2.1 任务下发到 HMI 端
      └─ HMI 拉取任务详情（Prompt 列表、配置、Metric 字段定义）
           │
           ▼
  2.2 HMI 执行单个 Prompt
      └─ 用户在 HMI 上点击「开始测试」
      └─ HMI 自动按顺序启动：
          ├─ movax（运动控制）
          ├─ 本体轨迹记录（关节数据采集）
          └─ MozTrace 日志记录（推理日志）
      └─ 各组件启动成功后返回状态，全部就绪后开始
      └─ 如果组件启动超时（30s），提示失败，支持重试/终止
           │
           ▼
  2.3 执行中数据记录
      └─ 实时记录：
          ├─ 本体运动轨迹（关节角度、速度、力矩、末端位姿）
          ├─ MozTrace 日志（推理输入、Action Chunk、推理耗时）
          └─ 三方视频（如果配置了外部摄像头，按时间戳打点）
      └─ 用户填写 Metric 字段（根据评测集定义的字段动态生成表单）
      └─ 支持异常操作（急停、复位、手动移动、终止测试）
           │
           ▼
  2.4 单次执行完成
      └─ 生成一个 Segment（包含过程数据 + Metric 结果）
      └─ 如果配置了多次执行（repeat_count），重复 2.2-2.4
      └─ HMI 显示当前进度（已完成 / 总数）

┌─────────────────────────────────────────────────────────────────┐
│ 阶段 3: 数据上传与落湖                                           │
└─────────────────────────────────────────────────────────────────┘
  3.1 自动上传（测试结束后触发）
      └─ 上传内容：
          ├─ 轨迹文件（本体数据）
          ├─ MozTrace 日志文件
          ├─ 三方视频文件
          └─ Metric 结果（JSON）
      └─ 通过统一的测试 ID 关联所有数据
      └─ 支持断点续传（网络异常时恢复后继续）
      └─ HMI 显示上传进度和状态
           │
           ▼
  3.2 数据标准化处理（平台侧异步）
      └─ 格式转换（统一为 parquet 等标准格式）
      └─ 时间对齐（多路数据按时间戳对齐）
      └─ 元数据索引（提取关键字段用于检索）
      └─ 质量评估（自动计算 quality_score）
           │
           ▼
  3.3 Segment 入库
      └─ 原始过程数据存入数据湖
      └─ 结构化元数据和 Metric 同步到 OLAP 引擎
      └─ 更新评测任务状态（执行中 / 已完成）

┌─────────────────────────────────────────────────────────────────┐
│ 阶段 4: 分析与回流                                               │
└─────────────────────────────────────────────────────────────────┘
  4.1 聚合分析（平台侧）
      └─ 按维度统计：
          ├─ 任务总览（各 Metric 平均得分、各 Policy 对比）
          ├─ Prompt 维度（按场景标签统计通过率、失败分布）
          ├─ 版本对比（Policy v1.6 vs v1.5 性能差异）
          └─ 失败归因（失败类型分布、Top N 问题）
      └─ 生成评测报告（自动 / 手动触发）
           │
           ▼
  4.2 BadCase 标注与回流
      └─ 筛选失败的 Segment（标记为 BadCase）
      └─ 人工标注失败分类和原因
      └─ 一键回流到训练数据湖
      └─ 触发 DAgger 训练或微调
           │
           ▼
  4.3 版本回归测试
      └─ 新模型用同一 Benchmark 再次评测
      └─ 对比性能变化，验证优化效果
```

## 7. 页面与交互建议

以下页面建议基于文档中明确出现的流程和字段，未包含过度设计的内容。

### 7.1 评测集管理页面

**页面结构：**
- 评测集列表（表格形式）
  - 列：评测集名称、版本、场景标签、Prompt 数量、创建时间、操作
  - 操作：编辑、复制、标记为 Benchmark、删除
- 创建/编辑评测集页面
  - 基本信息：名称、版本号、场景标签、描述
  - Prompt 列表：支持批量导入或逐条添加
  - 自定义 Metric 字段：字段名 + 值类型（下拉选择）
  - 任务级预设配置（可选，JSON 编辑器）
  - 保存为模板：勾选后可在模板库中使用

**来源：** 文档3 "评测集（Evaluation Set）"、文档4 "自定义 Metric 字段"

### 7.2 评测任务管理页面

**页面结构：**
- 任务列表（表格形式）
  - 列：任务名称、评测集、模型列表、状态、创建时间、操作
  - 操作：查看详情、复制任务、删除
- 创建评测任务页面
  - 选择评测集或 Benchmark
  - 指定被测模型（支持多个）：Policy 名称、版本、ckpt 路径、代码分支
  - 执行参数配置：每个 Prompt 测试次数、超时时长
  - 选择测试机器（从 IP 列表中选择）
  - 上传 config JSON（可选）
- 任务详情页面
  - 基本信息标签：任务配置、执行状态
  - 统计分析标签：各 Metric 平均得分、各 Policy 对比图表
  - Segment 列表标签：展示所有测试记录，支持筛选
  - 生成报告按钮

**来源：** 文档3 "评测任务（Evaluation Task）"、文档1 需求拆解

### 7.3 HMI 评测执行界面

**页面结构：**
- 任务信息区域：显示任务名称、当前 Prompt、进度（已完成/总数）
- Prompt 显示区域：显示当前 Prompt 文本，支持现场编辑
- 组件启动状态区域：显示 movax、本体轨迹、MozTrace 的启动状态（等待中/启动中/成功/失败）
- 控制按钮区域：
  - 开始测试（启动所有组件）
  - 异常操作按钮：急停、复位、手动移动、终止测试
  - 手动保存按钮
- Metric 填写表单：根据评测集定义的字段动态生成，包含对应的输入控件
- 上传进度区域：显示数据上传进度和状态

**来源：** 文档1 "一键启动测试"、文档4 "动态表单生成"

### 7.4 Segment 详情页面

**页面结构：**
- 基本信息标签：Segment 元数据（任务、Prompt、Policy、执行时间等）
- Metric 结果标签：展示填写的 Metric 字段值
- 轨迹回放标签：可视化展示关节数据时间序列图表
- 日志查看标签：MozTrace 日志内容，支持关键词搜索和时间轴跳转
- 视频回放标签：展示三方视频（如果有），支持裁剪播放
- 联动回放功能：视频进度条与轨迹图表同步
- 操作按钮：回流 DAgger（如果是 BadCase）

**来源：** 文档3 "Segment" 数据结构、文档1 "可观测性"

### 7.5 数据分析页面

**页面结构：**
- 版本对比页面：选择两个 Policy 版本和评测集，展示差异图表和明细

### 9.2 两端联动的关键流程

以下流程需要 HMI 采集端与已有评测平台协同完成：

#### 流程 1: 任务下发与执行

```
已有评测平台                           HMI 采集端

    ├─ 1. 创建评测任务                      │
    ├─ 2. 配置评测集、模型、执行参数          │
    ├─ 3. 任务下发 ────────────────────────>│
    │                                      ├─ 4. HMI 拉取任务详情
    │                                      ├─ 5. 显示 Prompt 列表和 Metric 字段定义
    │                                      ├─ 6. 用户点击"开始测试"
    │                                      ├─ 7. 自动启动组件（movax/轨迹/MozTrace）
    │                                      ├─ 8. 执行测试并记录过程数据
    │                                      ├─ 9. 用户填写 Metric 表单
    │<─ 10. 数据上传 ──────────────────────┤
    ├─ 11. 接收数据并存入数据湖              │
    ├─ 12. 更新任务状态                      │
    └─ 13. 可查看结果和分析                  │
```

**待确认问题：**

### 11.2 建议一期优先做的能力（综合评估）

在 P0 基础上，建议增加以下 **P1 能力**，理由是它们与 P0 能力强相关，合并实现可形成完整闭环：

| 功能模块 | 核心能力 | 交付标准 | 选择理由 |
|---------|---------|---------|---------|
| **任务执行** | 一键启动测试 | HMI 自动启动 movax、本体轨迹、MozTrace，显示启动状态 | 与 P0 的"解除头显限制"配合，形成完整的执行流程 |
| **过程数据** | 全链路数据记录 | 记录本体轨迹、MozTrace 日志、三方视频，带统一测试 ID | 与 P0 的"数据导出规范"配合，确保数据完整性 |
| **数据上传** | 自动上传与关联 | 测试结束后自动上传，支持断点续传，显示上传进度 | 与数据湖接入配合，形成数据闭环 |
| **配置管理** | 评测模板管理 | 支持保存评测集配置为模板，模板库可浏览和选择 | 与 P0 的"Metric 配置"和"Prompt 管理"配合，提升配置复用效率 |

### 11.3 建议一期 MVP 范围（最小可交付）

**核心原则：** 优先打通"配置 → 执行 → 数据采集 → 存储 → 基础分析"的完整链路，确保端到端可用。

#### 阶段 1: 配置准备（2周）

**已有评测平台侧：**
- [ ] 评测集管理页面：创建、编辑、列表
- [ ] 自定义 Metric 字段配置：字段名 + 值类型
- [ ] Prompt 批量导入功能
- [ ] 评测任务管理页面：创建、配置、列表
- [ ] 评测模板库：保存和选择模板

**交付标准：** 用户可以在平台上创建评测集、配置 Metric 字段、创建评测任务

#### 阶段 2: 执行与采集（3周）

**HMI 采集端改造：**
- [ ] 任务接收功能：拉取平台下发的任务详情
- [ ] Metric 动态表单生成：根据评测集定义生成输入表单
- [ ] 解除头显启动限制
- [ ] 一键启动测试：自动启动 movax、本体轨迹、MozTrace
- [ ] 组件状态监控：显示各组件启动状态
- [ ] 过程数据记录：本体轨迹、MozTrace 日志、三方视频（可选）
- [ ] 数据自动上传：测试结束后上传，支持断点续传
- [ ] 异常操作按钮：急停、复位、终止测试

**交付标准：** 用户可以在 HMI 上执行评测任务，填写 Metric 结果，自动上传数据

#### 阶段 3: 数据存储与检索（2周）

**已有评测平台侧：**
- [ ] 数据湖扩展：评测集/评测任务/Segment 数据模型
- [ ] 数据接收接口：接收 HMI 上传的数据
- [ ] 数据标准化处理：格式转换、时间对齐、元数据索引
- [ ] Segment 列表页面：展示评测记录
- [ ] 多维度筛选：按评测集、模型、场景、Prompt 筛选
- [ ] Segment 详情页面：展示元数据、Metric 结果

**交付标准：** 评测数据可以存入数据湖，用户可以查询和查看详情

#### 阶段 4: 基础分析（1周）

**已有评测平台侧：**
- [ ] 任务总览统计：各 Metric 平均得分、各 Policy 对比图表
- [ ] 数据导出功能：清晰对应 T1/T2/T3 结果，导出 CSV

**交付标准：** 用户可以查看任务统计结果，导出数据进行离线分析

### 11.4 不建议一期做的能力（后置到 P2）

| 功能模块 | 原因 | 建议时机 |
|---------|------|---------|
| **轨迹回放** | 需要复杂的可视化和播放控制，依赖数据格式统一 | P2，数据积累后再做 |
| **BadCase 回流** | 需要与训练数据湖对接，流程复杂 | P2，评测闭环稳定后再做 |
| **离线评测** | 需求细节不明确，可能涉及仿真环境 | P2，具体方案明确后再做 |
| **失败分类管理** | 需要先定义分类体系，依赖业务方输入 | P2，分类体系明确后再做 |
| **权限管理** | 一期可以简化为单一角色或开放访问 | P2，多团队协作时再做 |
| **SQL 取数** | 一期基础分析 + 数据导出已足够 | P2，高级分析需求明确后再做 |
| **跨机器验证** | 需要复杂的回放机制，需求优先级低 | P2 或更晚 |
| **代码自动解析部署** | 一期可以手动配置依赖，自动解析复杂度高 | P2，部署频繁后再优化 |

### 11.5 需要业务方确认后才能定范围的能力

| 功能模块 | 不确定因素 | 对一期范围的影响 |
|---------|-----------|----------------|
| **Prompt 现场编排** | 修改后的版本管理机制未明确 | 如果需要生成新版本，开发量较大，建议一期仅支持临时修改 |
| **配置逻辑解耦** | config JSON 的 schema 和加载机制未明确 | 如果 schema 复杂，建议一期仅支持简单参数覆盖 |
| **三方视频集成** | 摄像头配置和管理方式未明确 | 如果需要复杂的摄像头管理，建议一期标记为"可选" |
| **代码版本部署** | 依赖解析规则未明确 | 建议一期仅支持指定 branch + 手动配置依赖，自动解析放到 P2 |

### 11.6 一期 MVP 时间估算（粗略）

| 阶段 | 工作量（人周） | 备注 |
|------|-------------|------|

| 阶段 2: 执行与采集 | HMI 端 3周 | HMI 端改造 |

- 实际排期需要确认开发资源和依赖关系后再精确评估

### 11.7 风险与依赖
